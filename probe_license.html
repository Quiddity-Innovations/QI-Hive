OnBase Licensing Probe

Two routes to the licensing question. They target different systems — read the banner on each tab.
Target: local VM 192.168.251.128 → SQL Server → database Nautilus, schema hsi — OnBase 13. Reads the database directly, bypassing OnBase entirely. Consumes no license seat.
Probe 1 — row counts across the licensing tables, full dumps of primarylic / secondarylic / licensedproduct / licensedproductcontrol / licensecontrol, non-PII columns of licensetable, plus index and declared-type introspection.
Probe 2 — the full systemtableex row, every hsi table matching %lic%/%regist% by row count, registeredusers with machine identifiers masked, and the useraccount.licenseflag distribution.
Certificate and hash blobs are reported by length and prefix only — never dumped in full. If the VM has been rebooted, VMware NAT may have moved it: change the host above rather than editing the scripts.
Target: local VM 192.168.251.128:8088 — the guest-side Unity JSON microservice (poc\guest_unity_service.ps1) fronting OnBase 13. Reads live through the Application Server, not the database. Live and enabled — a successful run holds the guest's existing MANAGER session; it does not open a new one.
Target: BU's Hyland Cloud, OnBase 25, over the Unity Client SOAP transport. Not the same system as the SQL tab, and not the same OnBase version as the live option above.
Outbound connections to BU are disabled. On 6 Aug 2026 every BU environment was set "enabled": false, and this page cannot opt back in — the runner never sets ONBASE_API_PROBE_ENABLE. Re-enabling is a deliberate act at a shell, requiring both gates to be opened by hand.
The button below runs local filesystem checks only against a BU selection and makes no network call of any kind.
Confirms the Application Server actually grants a session (the licensing fact SQL cannot see), lists the entitlement surface — which of the 17 configuration collections this account can reach — and compares API vs SQL counts for document types, user accounts and user groups. A gap between them is security trimming, not error: the API returns only what the account is entitled to see.
Reports each BU prerequisite independently: config readable, environment enabled or locked, bridge binary present, Unity Client assemblies installed, credentials available. When the API route cannot run, which prerequisite is missing is the whole answer.
The OnBase 13 route reuses the guest's already-open MANAGER session, so running it does not consume an additional seat. The BU route, if ever re-enabled, would consume a Unity Client seat per call, stranded 20–60 minutes on an ungraceful kill.
